一、SQL 注入

1.1 什么是 SQL 注入

程序把用户输入当成字符串拼进 SQL 语句，数据库解析时无法区分”哪部分是程序员写的语句、哪部分是用户输入的数据”，于是输入里的 '、#、union 被当作语法执行。

1.2 成立需要三个环节

环节 说明
① 可控输入点 GET / POST / Header / Cookie 只要有一个没走参数化就算
② 拼进语句 用字符串拼接构造 SQL，而不是占位符
③ 无参数化 没有 bind_param / PDO 预处理

三个环节里断掉任何一个，注入就不成立。

1.3 分类维度

同一个漏洞从三个角度看，会得到三张不同的表，实际测试时是叠着用的：

维度 类型
按请求位置 GET 注入 / POST 注入 / Header 注入 / Cookie 注入
按变量类型 数字型 / 字符型 / 搜索型（LIKE）/ XX 型（括号包裹）
按 SQL 语句 select / insert / update / delete——语句类型决定回显位和可用手法
按回显方式 联合查询（有回显）/ 报错注入 / 布尔盲注 / 时间盲注

1.4 通用判断流程

1.5 闭合类型

关卡 拼接后的样子 闭合 payload 开头
数字型 where id=$id 不需要闭合，直接 1 and ...
字符型 where username='$name' vince' #
搜索型 where username like '%$name%' vince%' #
XX 型 where username=('$name') vince') #
数字型（delete） where id=$id 不需要闭合，直接 1 or ...

# 是 MySQL 的行注释，作用是把后面多余的引号、括号、% 全部吃掉。

3.4 Header 注入：藏在请求头里的输入点

输入点不止表单。 只要一个值会被写进 SQL，它就是注入点，而 Header 往往是最容易被漏测的地方——扫描器默认只测 GET/POST 参数，User-Agent、X-Forwarded-For、Referer、Cookie 都需要手动加。

这一关还有个手法上的必然：insert 语句没有回显位，不能用 union select，所以只能用 extractvalue / updatexml 这类报错函数，或者干脆上时间盲注。

3.7 宽字节：转义函数为什么会失效

mysqli_real_escape_string 做的事是把 ' 前面加一个 \（0x5C）。但 GBK 是双字节编码，首字节范围 0x810xFE、尾字节范围 0x400xFE，而 0x5C 正好落在尾字节范围内：

于是引号逃逸出来了。修法不是”再过滤一次”，而是统一字符集：页面、连接、表、字段全部 utf8mb4，并在连接后显式执行 set names utf8mb4，让转义函数工作在它假设的单字节环境里。

3.8 成因归纳

10 个关卡对应 10 种输入位置、变量类型和语句类型，但根因只有一条：用拼接构造 SQL。

四、修复方案

SQL 注入的修复原则只有一条：不要让用户输入参与 SQL 语句的构造。所有查询一律改成预处理语句（prepare + bind_param），数字型顺手 intval，like 里的 %、_ 用 addcslashes 转义；表名、排序字段、limit 偏移量这类占位符管不到的地方，用白名单枚举而不是过滤。再往上，关闭 display_errors 不把 SQL 报错结构送给攻击者、业务账号只给最小权限（禁 drop/file）、页面与连接统一 utf8mb4 并显式 set names（避免宽字节把转义符吃掉）、WAF 拦 union select、sleep( 这类特征，都算加固。
