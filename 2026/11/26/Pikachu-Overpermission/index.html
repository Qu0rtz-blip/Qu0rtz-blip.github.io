皮卡丘（Pikachu）越权通关记录

实验环境：Windows 10 + Pikachu + Burp Suite
靶场地址：http://127.0.0.1/pikachu/

本次记录皮卡丘靶场 Over Permission（越权）模块两个关卡的通关过程。
越权不是一个”技术点”，而是一个”校验点”：功能本身没写错，错在该校验的地方没校验。
水平越权是横向借别人的数据，垂直越权是纵向借别人的权限。

一、越权

1.1 两个方向

越权的定义很朴素：用 A 的身份，做了 B 才能做的事，而且做成了。按”越”的方向分两种：

它和”未授权访问”容易混：未授权是根本没登录就进了页面；越权是登录了，但用了不属于自己的身份/权限。两者的根因也一致——后台把”该不该给”交给了前端传来的参数，而不是服务端的登录态。

1.2 常见出问题的地方

皮卡丘概述页说得很准：越权容易出现在权限页面的增、删、改、查上。因为这些操作通常需要三个要素，缺一个就可能出事：

三种典型错法：① 用了前端传的值冒充（水平越权的经典）、③ 只在部分页面做了校验（垂直越权的经典）、② 直接拿 ID 查库不比对归属（改 ID 就能改别人的数据）。

1.3 关卡入口

两个小题用的是不同的账号体系：op1 是会员表（member，如 lili/123456），op2 是用户表（users，普通用户 pikachu/000000、管理员 admin/123456）。

三、源码分析：漏洞是怎么写出来的

3.1 关卡：用前端传的值代替登录态（水平越权）

op1_mem.php 的核心代码：

代码分析：

  • 登录校验只做了”有没有登录”（check_op_login），**没做”登录的是不是这个人”**；
  • 查询条件 $username 直接来自 $_GET，而 Session 里明明存着 $_SESSION['op']['username']——正确写法应该是 $username = $_SESSION['op']['username']，连参数都不需要；
  • 顺带一提：这里用 escape() 转义了，防住了 SQL 注入，但防注入不等于防越权——两件事。

  • op2_admin_edit.php 只校验了登录状态，任何 level 的用户都能进——包括 level=2 的普通用户、level=3 的 test 用户；
  • 源码注释同样直接点破：”这里只是验证了登录状态，并没有验证级别”；
  • 这个模式的现实版非常常见：菜单按权限渲染了（前端看不到按钮），但接口忘了校验——**前端隐藏不是权限控制，只是”眼不见”**。

把两关并排看，越权的成因其实只有一句：权限判断应该由服务端基于登录态计算，任何来自前端的”我是谁/我要操作谁”都不能直接当权限依据。

四、修复方案

越权的修复原则只有一条：每一个涉及数据或功能的操作，都在服务端用登录态重新算一遍权限。具体三条：① 身份只认 Session/Token 里的值，绝不接受前端传的 username、userid 当”我是谁”；② 水平方向——查询、修改、删除前先校验数据归属（where id=? and owner_id=?，或先查出来再比对 owner_id == session.user_id，不匹配返回 403 而不是 404 之外的花样提示）；③ 垂直方向——把权限校验做成统一拦截器/中间件（路由级注解或 before 钩子），按”角色-功能”矩阵校验，而不是在每个页面里手写 if，只要有一个页面漏写就是缺口。再往上，ID 用不可枚举的 UUID、敏感操作二次验证（改密码要原密码）、权限变更记审计日志，都算加固。
