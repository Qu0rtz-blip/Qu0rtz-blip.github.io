一、PHP反序列化

1.1 序列化与反序列化

PHP 里有两个互为逆操作的函数：

  • serialize()：把一个对象（或数组等）压平成字符串，方便存储和传输；
  • unserialize()：把这个字符串还原回对象。

这段字符串的格式值得逐字符读一遍：

    O:代表object

    S:对象的名称

    s:数据类型
    7:变量值的长度

O（object）、s（string）、i（int）、a（array）这些前缀就是 PHP 自己的序列化协议。长度数字必须和实际内容一致，这也是手工构造 payload 时最容易出错的地方。

1.2 魔法方法：漏洞的引爆点

危险在哪：unserialize() 的输入如果是用户可控的，攻击者就能凭空”复活”任意类的一个对象，属性值随便填；如果这个类（或它关联到的其他类）存在魔法方法，方法体里又拿属性去 echo、拼接 SQL、调函数——属性里的恶意内容就顺着魔法方法被执行了。

这条”从用户可控的序列化串 → 魔法方法 → 危险操作”的链路，就是反序列化漏洞的完整成因。Pikachu 这一关是最短的一种链：反序列化后的属性被直接 echo 出来。

三、源码分析：漏洞是怎么写出来的

unser.php 的核心代码（其余都是页面模板）：

代码分析：

  • unserialize($_POST['o']) 把 POST 参数原样交给反序列化函数，没有任何校验——这是漏洞的第一环：对象的内容完全由用户决定；
  • 第二环是 echo "{$unser->test}"：反序列化出来的对象的属性被直接拼进 HTML 输出，中间没有 htmlspecialchars()，属性值里是什么标签就渲染什么标签，于是”改属性值”变成了”注入 HTML/JS”；
  • 有意思的是代码里的 __construct()：它也会 echo $this->test，看起来像第二条利用路径。但 PHP 的 unserialize() 不会调用构造函数（__construct 只在 new 时触发），所以这条路径实际走不通——真正起作用的只是下面那句 echo $unser->test。

unser.php 将 POST 参数 o 未经校验交给 unserialize()，攻击者可构造 O:1:"S":1:{s:4:"test";s:N:"<payload>";} 完全控制对象属性；随后属性值经字符串插值直接输出到 HTML，未做实体转义，形成反射型 XSS。由于类 S 仅定义 __construct()，而 unserialize() 不触发构造函数，且不存在 __wakeup()／__destruct() 等可触发的魔术方法，本例不存在可用的 gadget 链，危害为 XSS 而非远程代码执行。修复只需对输出做 htmlspecialchars()，根本修复应避免反序列化不可信输入或启用 allowed_classes 白名单。

四、修复方案

反序列化的修复原则只有一条：永远不要 unserialize() 用户可控的输入。确需跨端传对象状态时，改成 JSON（json_encode / json_decode）这类不重建对象的数据格式；实在无法避开（如内部系统间传递），先用 serialize 的签名机制（对序列化串做 HMAC 后随包携带，反序列化前先验签），并把可反序列化的类收紧到白名单——PHP 7.2+ 可以给 unserialize() 传第二个参数 allowed_classes（如 unserialize($s, ['allowed_classes' => false]) 直接禁止还原任何对象），代码评审里把”反序列化外部输入”列为禁止项。再往上，对象属性输出到页面时统一 htmlspecialchars()、升级 PHP 7.4+ 让 __wakeup 等被滥用时至少有版本层面的缓解、WAF 拦 O:\d+:" 这类序列化串特征，都算加固。
