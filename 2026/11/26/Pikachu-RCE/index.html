一、RCE

RCE（Remote Code Execution）不是一个具体的漏洞点，而是一类后果：任何能让攻击者的输入最终变成”被解释器执行的代码或命令”的缺陷，都归到这一类——eval、include、反序列化、命令拼接、模板注入，都是它的入口。

两者的区别值得记一下：代码执行在 PHP 进程内，能用 PHP 的全部函数、能读到数据库配置和会话；命令执行是另起一个系统进程，拿到的是操作系统层面的能力，更容易直接落地成一个 shell。所以同样是一句话木马，写在 eval 里和写在 shell_exec 里，后续利用的路子是不一样的。

再往下走：system('id');

eval 里可以调用任意 PHP 函数，system 会把命令的标准输出直接打到页面上，回显是 www-data。

比如：system('id')?>。

三、源码分析：漏洞是怎么写出来的

3.1 关卡 5-1：eval 直接吞下用户输入

rce_eval.php 的实际源码：

代码分析：

  • eval() 在 PHP 里是语言结构而不是函数，它不返回执行结果，而是把字符串当作 PHP 代码当场编译执行——所以这里等于把 PHP 解释器交给了任何一个能打开页面的人；
  • @ 只是压制错误提示，不影响执行；
  • 判断条件 @!eval(...) 是错的：eval 执行一条语句后返回 null，!null 为 true，于是无论代码执行成功与否，都会走进 if 分支打印那句话。这句提示不能当作”输入有误”的信号；
  • 没有白名单、没有关键字过滤、没有长度限制——eval($_POST['txt']) 这七个字就是全部防护。

3.2 关卡 5-2：命令拼接

rce_ping.php 的实际源码：

代码分析：

  • shell_exec 把整串交给系统 shell 解释（Linux 是 /bin/sh -c，Windows 是 cmd /c），所以分隔符、管道、重定向、子命令全部可用，ping 只是这条命令的第一个词而已；
  • Windows / Linux 两个分支只改了 ping 的参数（-c 4），拼接方式完全一样，所以两个平台都能打，只是分隔符习惯不同；
  • 回显用 if($result){ echo "<pre>{$result}</pre>"; } 直接输出，等于白送一个命令回显终端。

那行注释掉的 $check 就可以修复这个问题：对输入先做 IP 段校验，校验完后再执行。

四、修复方案

RCE 的修复原则只有一条：不要让用户输入进入代码或命令的解析过程。能用内置函数解决的，不要调外部命令（例如判断主机存活可以用 gethostbyname() / fsockopen()，没必要 ping）；必须调外部命令时，用 escapeshellarg() 逐个转义参数，或者直接用 proc_open() 的数组形式传参（数组形式不经过 shell，分隔符会失去意义）；同时把 eval、assert、system、exec、shell_exec、passthru、popen 这类函数写进 disable_functions，代码评审里禁止出现 eval。再往上，对 IP 这类输入用 filter_var($ip, FILTER_VALIDATE_IP) 做强校验、Web 进程用低权限账号并在容器里运行、WAF 拦截命令分隔符，都算加固。
