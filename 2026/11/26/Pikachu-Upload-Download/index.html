皮卡丘（Pikachu）不安全文件上传与下载通关记录

实验环境：Windows 10 + Pikachu + Burp Suite + 蚁剑
靶场地址：http://127.0.0.1/pikachu/

本次记录皮卡丘靶场 Unsafe File Upload 与 Unsafe File Download 两个模块的通关过程。
这两个漏洞是一对镜像：上传是”让服务器执行我给的文件”，下载是”把服务器的文件拿回来看”，
入口形状几乎一样——一个来自前端的文件名。放在一起打，对根因的理解会清楚很多。

一、不安全文件上传与下载

1.1 两个功能，一个根因

上传和下载在 Web 系统里无处不在：头像、附件、报表导出、资源下载。它们的实现流程是镜像的：

两边的安全设计也指向同一件事：文件名/路径不能由前端决定。皮卡丘把这两条线各拆成一关组，后台代码里”来自前端的文件名直接拼进路径”的写法原封不动地摆在那儿，区别只在利用方式：

一句话：上传送进去的是代码，下载带出来的是内容。它们也常常配合——下载读到数据库配置、源码，往往就是下一轮上传/包含利用的钥匙。

1.2 关卡入口

上传模块三关页面长得一样：一个”这里只允许上传图片o！”的文件选择框；下载模块是”NBA 1996年 黄金一代”球员头像列表，提示”点击球员名字即可下载头像图片”。

2.6 下载·失败长什么样

传一个不存在的文件名，页面直接跳回提示”你要下载的文件不存在，请重新下载”。这说明后台有 file_exists() 检查——payload 必须指向真实存在的文件，但换个角度，它也把”猜路径”变成了有反馈的试错：存在就下载、不存在就提示，等于一个免费的文件存在性探测接口。

三、源码分析：漏洞是怎么写出来的

上传三关共用 inc/uploadfunction.php，里面的三个函数就是三道防线的三个版本；下载关是独立的 execdownload.php。四个入口，同一个病根。

3.1 上传·客户端 check——校验写在了浏览器里

clientcheck.php 的”校验”是一段前端 JS：

绑在文件选择框的 onchange 上。而后台调用的 upload_client() 里没有任何后缀检查，直接 move_uploaded_file 存盘：

问题在于：JS 跑在浏览器里，Burp 改包的瞬间它已经出局了。另外两点也值得记：原样使用用户上传的文件名（可以覆盖同名文件、可以带特殊字符），上传成功后还把完整路径 {$upload['new_path']} 直接打印在页面上——源码作者自己都注释了一句”输出了路径，暴露了”。

3.2 上传·服务端 check——校验了可以伪造的字段

servercheck.php 调用 upload_sick()，服务端确实做了一次检查：

校验虽然挪到了服务端，但选错了字段：$_FILES['type'] 来自请求头体里的 Content-Type，由客户端声明，Burp 一改就过。校验的字段必须是服务端自己能验证的事实（文件后缀、文件内容），而不能是客户端的请求。

且这里做的是白名单校验，像shell.php.abc或者字符串截断这种都无法成功。

3.3 上传·getimagesize

getimagesize.php 调用严格的 uploadfunction()，五道检查值得逐条看：

和前两关对比，它做对了几件关键的事：后缀自己解析、小写化、白名单比对（堵住大小写、双后缀）；**getimagesize() 检查文件头（纯改名的马过不了）；随机重命名**（用户可控的文件名彻底出局，原文件名不再出现在磁盘上）。

但这里还有一个漏洞，就是getimagesize()函数

getimagesize()函数 不是完整性校验，它只解析图片头部/必要结构，拿到宽高和类型；图片数据之后追加的内容通常会被忽略。所以“合法图片头 + 任意追加数据”一般就能过。

而且后端分别检查了后缀、MIME 和 getimagesize() 返回的图片头，但没有校验三者是否一致，也没有对图片重新编码。我们使用 GIF89a 伪造图片头，把文件后缀改成 .jpg，声明 MIME 为 image/jpeg，即可绕过检查，形成图片马。若上传目录可执行脚本，或存在本地文件包含，则可进一步 RCE。

3.4 下载·拼接 + 探测反馈

execdownload.php 的核心代码（下载逻辑全文其实就这么一段）：

代码分析：

  • 唯一的漏洞点就是第一行："download/{$_GET['filename']}" 直接拼接，../ 原样进入路径，没有任何过滤、白名单或目录限定；
  • file_exists() 不是防护，反而帮了攻击者的忙——它把”猜路径”变成了有反馈的试错：存在就下载、不存在就提示，等于一个免费的文件存在性探测接口；
  • iconv("utf-8","gb2312",...) 只是为了中文文件名显示，纯 ASCII 的 payload 原样通过，不构成任何阻碍；
  • Content-Disposition: attachment + 字节流输出的写法本身是标准的，坏就坏在路径来源上——**下载功能的实现没错，错的是”信了前端传来的文件名”**。

把四个入口并排看，会发现校验的”位置”和”字段”决定了一切：写在前端=没有；写错字段=形同虚设；写在服务端、校验服务端能验证的事实=合格。下载关连校验都没有，只剩一个反而是帮倒忙的存在性检查。

四、修复方案

文件上传：校验必须全部发生在服务端，且校验的是服务端自己能验证的事实。后缀白名单（解析后小写比对，禁 php/phtml/.htaccess 等一切可执行后缀）、getimagesize()/finfo 校验文件真实内容、限制大小；文件名彻底放弃用户输入，随机重命名后保存；上传目录与网站目录分离或禁止执行（Nginx location ~* ^/uploads/.*\.php$ { deny all; }、Apache 用 php_admin_flag engine off），成功响应只返回文件 ID 而不是完整路径；再往上，图片二次渲染抹掉附加数据、上传接口限速鉴权，都算加固。

文件下载：不要让用户输入决定服务器的文件路径。最稳妥的做法是后端映射——前端传文件 ID 或枚举值，后端查表拿到真实文件名（图片根本没有必要让前端传名字）；确实要传文件名时，用 basename() 剥掉路径部分，拼上固定的下载根目录，再用 realpath() 校验最终路径仍在根目录之内，顺手把后缀限制在白名单里。再往上，下载目录单独建、只放可公开的文件，与上传目录和程序目录物理分开；open_basedir 限制 PHP 可访问范围；对同一 IP 的高频”不存在”请求限速（防探测）；静态文件下载交给 Web 服务器处理、动态接口只签发带过期时间的下载令牌，都算加固。
