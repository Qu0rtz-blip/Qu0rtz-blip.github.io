1.1 什么是文件包含

2.3 失败长什么样

传一个不存在的文件名（比如 filename=file999.php），页面基本是空白的——include 找不到文件只产生一条 warning，被页面模板吞掉了，不会像前面几关那样给固定文案。没有显式回显反而是好事：说明这是 include 而不是 require，包含失败不会中断脚本，可以放心试错。

三、源码分析：漏洞是怎么写出来的

3.1 关卡：本地文件包含的拼接

fi_local.php 的核心代码：

代码分析：

  • include "include/$filename" 是字符串拼接，$_GET['filename'] 里的 ../、php:// 会被原样拼进去，路径穿越和伪协议都是这么来的；
  • 拼接没有做任何过滤，也没限定后缀——传 file6.php 能读隐藏文件，传 ../../../../etc/passwd 能跳出目录；
  • 被注释掉的那段就是正确写法：白名单，只允许五个已知文件名。它摆在那儿是给你对比用的；
  • 页面里的下拉框只是”看起来限制了输入”，参数在 URL 里，改一下就能绕过——前端限制从来不算防护。

  • 连 include/ 前缀都省了，**整串交给 include**——本地路径、远程 URL、伪协议全部通吃；
  • 能不能打通远程只取决于 php.ini 的两个开关：allow_url_fopen（能不能打开远程 URL）和 allow_url_include（能不能 include 远程文件）。Pikachu 页面上那三行红字警告就是在检查这几个配置；
  • 源码里没有任何 str_replace、basename()、白名单——和本地那关一样，防护为零。

那三行红字其实也提示了一个事实：远程包含在默认配置下是关着的，这也是为什么现实里 LFI 远比 RFI 常见。

四、修复方案

文件包含的修复原则只有一条：不要让用户输入决定被包含的文件路径。业务上文件名应当由后端映射——前端传 ID 或枚举值，后端查表得到真实路径（$map = ['1'=>'file1.php', ...]），永远不要拼接。确实需要按名字包含时，先用 basename() 去掉路径部分，再用白名单校验，只允许固定后缀和固定目录，并用 realpath() 确认最终路径仍在允许的目录内（防止 ../ 穿越）。配置层面，allow_url_include 保持 Off（默认就是 Off，别为了”灵活”打开），open_basedir 限制 PHP 只能访问指定目录，关掉不必要的伪协议封装。再往上，上传目录禁止执行 PHP（php_admin_flag engine off）、把用户可写的目录排除在包含路径之外、WAF 拦 ../、php://、data:// 特征，都算加固。
