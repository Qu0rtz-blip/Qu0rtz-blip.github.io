一、SSRF

1.1 什么是 SSRF

SSRF（Server-Side Request Forgery，服务端请求伪造）：服务端提供了”从其他地址获取数据”的功能，却没对目标地址做限制，攻击者就能让服务器去请求任意地址，并把响应内容带回来。

关键在数据流向的变化：

这一步”代为请求”的价值在于：服务器处在内网。它能访问 127.0.0.1 上的服务、能访问只有内网才通的系统（数据库、Redis、管理后台、云元数据接口），而这些地址从攻击者所在的公网根本够不着。所以 SSRF 常被称作”内网跳板”。

2.5 失败长什么样

传一个不存在的内网地址（如 http://10.0.0.99/），页面基本空白、等一会儿才返回——连接超时。没有显式报错反而是有用的信号：超时说明地址不可达，秒回说明有服务在应答。盲 SSRF 的端口扫描就是靠这个时间差做的。

三、源码分析：漏洞是怎么写出来的

3.1 关卡：curl 全协议裸奔

ssrf_curl.php 的核心代码：

代码分析：

  • curl_init($URL) 直接吃下前端传来的 URL，没有协议白名单、没有 IP 黑名单、没有内网段过滤；
  • curl 默认支持 file://、gopher://、dict:// 等一大票协议（curl --version 能看到完整列表），所以”请求一个网页”这个动作天然就能扩展成读文件、发裸 TCP 报文；
  • echo $RES 把响应原样打印到页面上——有回显，这是这关打得顺的根本原因；真实场景里很多 SSRF 没回显，只能靠时间差和 DNS 外带判断；
  • 源码注释里那段 payload 提示（file:///etc/passwd、http://192.168.1.15:22）又一次说明：皮卡丘把”答案”直接写在了代码里。

  • 和 curl 版对比：函数不同、协议面不同，但漏洞的成因一模一样——把”请求哪个地址”的决定权交给了前端。

四、修复方案

SSRF 的修复原则只有一条：不要让用户输入决定服务器请求的地址。优先用”白名单”而不是”黑名单”——业务上只允许请求哪几个域名/IP，就写成固定列表去比对（in_array(parse_url($url, PHP_URL_HOST), $allow, true)），而不是去拦 127.0.0.1、169.254 这些特征（黑名单永远能被绕过：127.0.0.1 有 0.0.0.0、127.1、[::1]、十进制 2130706433 等十几写法，还有 xip.io 这类泛解析域名、302 跳转、DNS rebinding）。确实要请求外部地址时，用独立的出站代理或 egress 网关统一收口，并在网络层禁止 Web 服务器访问内网段和云元数据地址（169.254.169.254）；curl 场景下显式限制协议（CURLOPT_PROTOCOLS 只留 HTTP/HTTPS）、关闭跟随跳转（CURLOPT_FOLLOWLOCATION=false）或对跳转后的地址重新校验；file_get_contents 场景尽量不用它做”取内容”，改用带白名单的 HTTP 客户端。再往上，出站流量做日志与告警（异常的内网访问、非常规端口连接），比事后补救有效得多。
