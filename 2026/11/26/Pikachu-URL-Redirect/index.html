一、URL 重定向

1.1 什么是 URL 跳转漏洞

登录后跳回原页面、短链接跳转、支付完成跳商家页……”跳转”是个高频功能。实现方式通常是把目标地址作为参数传给后端，后端用 header("Location: ...") 或前端 location.href 完成跳转：

所以它常和 SSRF、OAuth 配置错误一起出现。皮卡丘这一关演示的是最基本的一条：改 url 参数，跳去任意站。

2.4 失败/无效的样子

传一个不存在的站内文件（url=notexist.php），页面依然跳转，只是落地页是 404——跳转本身不校验目标是否存在，它只负责把地址塞进 Location。这也说明后端对 url 的处理只有”是 i 吗”这一个判断，其余完全放过。

三、源码分析：漏洞是怎么写出来的

urlredirect.php 的核心代码：

代码分析：

  • header("location:{$url}") ：header()会发送 HTTP 302 响应，浏览器收到 302 后，会按 Location 跳转，这里直接把 GET 参数拼进响应头，没有协议白名单、没有域名白名单、没有同域校验；

  • 代码接收到 GET 参数后，没有进行parse_url解析，没有看是否以 / 开头，是否包含 // ，是否包含javascript:/data:

  • 顺带一个更隐蔽的风险：header() 不校验内容里的换行，如果中间件/PHP 版本允许，%0d%0a 注入还能扩展成响应头注入（CRLF Injection），在跳转之外伪造 Cookie、改写响应体；

  • 整段代码没有一处”白名单”字样，和皮卡丘其它关卡一样——它要演示的不是”绕过多强的校验”，而是”根本没有校验”。

四、修复方案

URL 跳转的修复原则是：跳转目标不能让前端随便指定，必须有白名单或强制同域。最稳的做法是不传完整 URL，传一个跳转标识（?to=home、?to=order_detail），后端用固定映射表换成真实地址；如果业务确实需要带参数，就只允许相对路径（拒绝以 http://、https://、// 开头），并用 parse_url() 取出 host 与白名单比对（注意 @、子域后缀、编码这些绕过写法，比对要基于解析后的 host 而不是字符串包含）。跳转到外部站点时，中间加一个”即将离开本站”的确认页，把完整地址展示出来让用户自己确认。再往上，header() 前过滤 \r\n（防响应头注入）、OAuth 的 redirect_uri 严格登记（精确匹配而非前缀匹配）、对跳转接口做频率限制，都算加固。
