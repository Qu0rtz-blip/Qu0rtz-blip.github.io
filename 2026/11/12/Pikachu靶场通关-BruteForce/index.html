皮卡丘（Pikachu）第一关「暴力破解」通关记录

实验环境：Windows 10 + Pikachu + Burp Suite Community + ffuf
靶场地址：http://127.0.0.1/pikachu/

本次记录皮卡丘靶场第一关「暴力破解」的完整通关过程。
这一关共四个递进的小关卡，每一关都在前一关的基础上加了一层”看起来有用”的防护； 打完四关之后回到源码，分析这些防护为什么会失效，以及正确的写法应该是什么。

一、Brute Force

暴力破解（Brute Force）的本质是不受限制的反复试错：只要服务端不区分人和机器、不限制尝试次数，攻击者就能拿字典把账号密码一个个试过去。

Pikachu 把这一个考点拆成四道递进的题，正好对应现实中四种”看着挺安全、其实纸糊”的防护：

四道题的入口都在同一目录下：

2.2 关卡 1-2：验证码绕过（on server）

页面：bf_server.php

现象：页面多了图形验证码。按正常流程试一次——输对验证码、密码故意写错 —> 提示username or password is not exists～；输错验证码 —> 提示验证码输入错误哦！。

看似安全，但是发现，只要不刷新页面，一直用同一个验证码重放，就不会出现“验证码输入错误”的提示词。
我们来验证一下，抓到包后，在Burp里右键Send to Repeater，将验证码修改为当前页面的正确验证码，点击Send。

第一个突破口就在这里：验证码校验完之后没有被销毁，只要这张图不改，它可以一直用下去，说明服务端根本没有”这个码只能用一次”的概念。

攻击步骤：与 1-1 完全一致，唯一的区别是 vcode 参数填当前页面上正确的验证码并保持不变。

这一关的真正问题：验证码防的是”机器自动识别图片”，但它的生命周期设计错了。
一次性凭证必须用一次就作废，否则它就是一张可以无限复印的门票。

2.3 关卡 1-3：验证码绕过（on client）

页面：bf_client.php

现象：输错验证码，页面弹出一个 alert 框。注意是浏览器弹窗，不是服务端渲染在页面里的错误提示——
这几乎可以直接断定：校验发生在前端。

两个验证，任选其一即可确认：

  • 改包验证：抓包发到 Repeater，把 vcode 改成任意错误值直接 Send。
    返回”username or password is not exists～”而不是”验证码错误”，说明后端压根没看这个字段；

  • 看源码验证：页面上 Ctrl+U 查看源代码，搜索 createCode， 能看到验证码的生成和比对两个函数都写在页面 JS 里（完整代码见3.3）。

攻击步骤：抓包后直接爆破，vcode 字段随便填（删掉这个参数也不影响结果），

一个容易误解的点：网上很多 wp 用”浏览器禁用 JavaScript”来通过这一关。能成功，但这只证明了”前端校验拦不住人”，不等于漏洞只在前端——真实原因是后端根本没有校验逻辑。禁用 JS 只是绕过手段，后端不校验才是漏洞根因。

三、源码分析：漏洞是怎么写出来的

3.1 关卡 1-1：暴力破解

bf_form.php 的实际源码：

代码分析：

  • 用了预处理：? 占位符 + bind_param('ss')，用户输入始终被当作数据而不是 SQL 片段，所以这里不存在 SQL 注入；
  • 失败提示统一为 username or password is not exists～，不区分”账号不存在”与”密码错误”，防用户名枚举；

看似没有毛病，但缺少了防暴力破解机制。

这段代码：

  • 没有失败计数器，没有时间窗，没有账号 / IP 锁定；
  • 没有验证码，没有递增延迟；
  • 第 1 次请求和第 10000 次请求，处理成本完全一样。

于是它的安全性只取决于密码本身有多难猜，而不取决于攻击者能试多少次。只要攻击者有时间，密码总会被猜出来。
安全不是逐行正确就能成立的，还需要”限流”这类横切在整条链路上的约束。

为什么爆破出一堆密码为 0 的无用包？

我们再回过头看源码第一句

在我用的500-worst-passwords.txt字典里，刚好有0这个密码，而在 PHP 中，字符串 "0" 被转换为布尔值时会被判定为 false。
因此，如果 FFUF 尝试的密码恰好是 0，或者在构造请求时，username 的值被解析为了假值，这个 if 条件就会直接短路失败。

  • 无回显的原因：当 if 条件失败时，PHP 直接跳过了内部所有的验证逻辑，原样返回了包含表单的初始 HTML 页面。因为没有进入查询阶段，自然没有报错或失败提示。

  • 过滤失效的原因：-fr 是用来过滤特定字符的（比如过滤掉“密码错误”的提示）。但由于 if 条件直接短路失败，页面里根本没渲染“密码错误”的提示词。既然没有特征词，-fr 就形同虚设，FFUF 对比响应包后，把这种“带有差异（请求了但没输出）”的请求当成了有效结果打印出来。

因此，我们可以摒弃负向过滤，改用正向匹配 -mr（Match Regex）来精准匹配成功特征。

3.2 关卡 1-2：验证码复用漏洞

bf_server.php 的实际源码：

  • 用户名、密码、验证码三层非空检查，一个不漏，且都走了独立分支提示；
  • 验证码比对时**两边都 strtolower**，大小写不敏感，避免了”用户看着是对的却提示错”的体验问题；
  • 验证码错误时直接终止在提示分支，不会往下走登录逻辑；
  • SQL 依然是 ? 占位 + bind_param('ss')，没有注入。

问题只剩一处，就在那行注释里：

验证码存在 $_SESSION['vcode'] 里，校验通过后既不 unset，也不重新生成，于是它的有效期等于整个会话的生命周期：只要不刷新页面、不带新请求去触发重新生成，这一串字符就一直有效。

这就是 2.2 里”不刷新页面，同一个验证码重放十几次都不报错”的直接原因。

正确的写法是校验完成后立即作废，并配合失败计数：

本质：把验证码当成了”会话级常量”，而不是”一次性凭证”。一次性凭证的价值在于”用一次就少一张”，一旦可以无限复用，它就退化成了一张装饰性的图片，对自动化爆破的阻挡作用为零。

3.3 关卡 1-3：纯前端校验漏洞

bf_client.php 的验证码由页面里的 JavaScript 生成

三行分别对应三个致命问题：

① 答案放在全局变量 code 里 控制台敲一个 code 回车，答案直接打印出来
② 答案被写进 #checkCode 的 value 页面上肉眼可见，抄下来即可，连控制台都不用开
③ 比对发生在浏览器里 curl / ffuf 根本不执行 JS，这道门对爆破工具等于不存在

安全的地方：字符表 36 个（0-9 + A-Z），Math.floor(Math.random() * 36) 与数组长度严格对应。出错时 createCode() 自动换一张新码、空值也有 alert，唯独把整段逻辑放错了地方。

服务端这边，PHP 只接收 username 与 password，没有一行与 vcode 有关的判断，
这正是 2.3 里把 vcode 参数删掉、或随便填一个值都能登录的原因。

成因：把”体验层的校验”和”安全边界的校验”混为一谈。前端校验的价值是少一次网络往返、即时给出提示；它无法承担安全职责，因为浏览器完全在攻击者手里——改 JS、禁用 JS、控制台读变量、直接构造 HTTP 请求。

因此，对于验证码等绕过就会造成损失的校验必须放在后端。

3.4 关卡 1-4：token 只防伪造，不防穷举

bf_token.php 的核心逻辑（省略页面渲染部分）：

token 的生成在 inc/function.php 里：

代码分析：

  • 生成前先 unset 旧值；
  • set_token() 放在请求末尾无条件调用，所以成功、失败都会换，旧 token 立刻作废；
  • 比对在服务端完成，前端只负责把值回显；
  • 随机性来自微秒时间 + 5 位随机前缀 + 随机后缀，拼出 23 位字符串，实际不可预测。

但它挡不住爆破，原因有三层：

  1. token 明文下发：<input type="hidden" name="token" value="...">，拿到页面就能抄走，前端没有任何保护它的能力；
  2. 一次性 ≠ 限次数：多线程下确实会失效，但攻击者只要”取 token → 提交 → 再取 token”，就能一直试下去。；
  3. 防错了对象：token 防的是 CSRF，它的前提是攻击者读不到响应内容（同源策略挡住了跨站读取）；而爆破时攻击者自己就是那个客户端，中间没有任何东西挡着他读 token。

因此，只要没有次数限制，密码照样可以爆破。

四、修复方案

防暴力破解的思路是提高穷举成本：登录失败计数 + 账号/IP 锁定 + 递增延迟；验证码必须由服务端生成和校验，且一次性使用、校验后立即销毁；登录失败的提示要统一，避免暴露账号是否存在。有条件的话再上多因素认证和 WAF 频率限制作为加固。
