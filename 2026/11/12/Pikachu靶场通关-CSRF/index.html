一、CSRF 跨站请求伪造

CSRF（Cross-Site Request Forgery）的本质是借用受害者的登录态，替他发一个他自己不知道的请求。

它成立需要三个条件同时满足：

条件 说明
① 用户已登录 浏览器里存着目标站点的有效 Cookie / Session
② 请求可被跨站构造 参数全部可预测（GET 拼 URL、POST 拼表单），无需用户输入任何秘密
③ 服务端只看 Cookie 只凭 Cookie 认人，不校验请求是否来自本站页面、也不校验一次性令牌

三者的关系是：Cookie 是浏览器自动附带的，攻击者控制不了它，但也不需要控制它——只要诱骗受害者在他自己的浏览器里发请求，浏览器就会乖乖把 Cookie 带上。

与 XSS 的区别（两者经常被混为一谈）：

维度 XSS CSRF
信任被谁利用 用户对站点的信任（在站点里执行我的代码） 站点对用户浏览器的信任（借用用户的 Cookie）
是否需要登录态 不一定 必须
攻击者能否读到响应 能 不能（浏览器同源策略的限制）
防御核心 输出编码 证明”请求是本人主动发的”

CSRF 的定义是“跨站”请求伪造。在真实环境中，恶意页面在攻击者的服务器（如 evil.com），受害者在目标网站（如 bank.com）。攻击者生成链接（如http://evil.com/csrf.html）后诱导受害者点击，受害者点击后，跨站发出请求，从而实现攻击。

2.3 CSRF(token)

第三关页面看起来和第一关一模一样，但抓包会发现请求里多了一个token字段：

这里没有正确的 token，伪造请求打不进去。这是防范 CSRF 攻击的一种标准手段。

服务端为当前会话生成不可预测的 Token，并将其渲染到页面或通过受同源保护的接口提供给前端。每次修改状态的请求都必须携带该 Token，服务端验证后才执行操作。

攻击站点受同源策略的限制既不能读取目标网站页面，也不能读取 Token，因此无法构造通过校验的请求。Token 必须防泄露；若存在 XSS ，攻击者可能读取 Token，因此仍需防范 XSS。

这段代码只检查是否登录，即Session里有没有username，但没有检查这条请求是不是本人主动提交的。

攻击者只要骗受害者访问一个页面，浏览器就会自动带上PHPSESSID cookie，服务器校验cookie通过，就会执行请求。

这两关的区别只是”参数放在哪”：URL 里可以做成链接，请求体里只能做成表单。对服务端而言，两边的校验一模一样——都没有。

3.2 Token 关：多出来的那一个 == 就是全部防护

token 的生成在 inc/function.php：

  1. 每次请求都重新生成：set_token() 放在页面末尾无条件调用，打开一次页面换一次，重放必然失效；
  2. 绑定会话：值存在 $_SESSION['token']，别人的会话拿不到；
  3. 攻击者读不到：它被渲染在受害者的页面里，恶意页面受同源策略限制读不到目标站点的响应。

这也解释了 CSRF 与 XSS 的分工：如果这个站点同时存在 XSS，攻击者就能在受害者浏览器里用同源请求读页面、顺手把 token 读出来。XSS 可以击穿 CSRF token，这也是为什么 XSS 的危害等级通常更高。

四、修复方案

修复 CSRF 的关键是给写操作加与会话绑定的 CSRF Token（严格比较、用后轮换、不要放进 URL），同时把改数据的操作从 GET 改成 POST。再辅以 Cookie 的 SameSite 属性、Origin/Referer 白名单校验，改密码、转账等重要操作再加一道二次验证即可。
